# 开发记录：把 Node 版「点歌发语音条」移植成 NeoBot 2.0 插件

这份记录按时间顺序记下**为什么这么改**，以及**哪些地方踩了坑**。
想直接用插件的人看 [README](../README.md) 就够了；想知道「这行为什么长这样」的看这里。

- 起点：DSH / qq-agent 的 Node 版插件（`index.js` 1480 行 + `logic.js` 1465 行 + `netease-client.js` 516 行）
- 终点：NeoBot 2.0.2a9 的 Python 插件（`__init__.py` + 5 个模块，约 3500 行）
- 上游版本：1.7.0（功能集与判据全部对齐）

---

## 1. 先搞清楚源插件是怎么挂上去的

读 `index.js` 的头注释就能看出，原实现是被框架逼出来的：

1. 框架的 5 个 hook（before-context / before-llm-messages / after-response /
   before-tool / after-tool）**只在已经排定一次模型会话之后**才触发，而且上下文里
   没有 sender —— 既看不见「没触发会话的消息」，也没法主动发消息。
2. 所以它包了一层 `Orchestrator.prototype.onIncoming`：那是每条入站消息的必经点，
   `this` 上挂着完整的发送管道。
3. 命中「点歌」后**不调用原方法** → 宿主的唤醒倒计时不会排上 → 模型根本不跑（0 token）；
   再把这条消息 `markEntryRead()` 标已读，避免重复响应。

也就是说：**0 token 不是省出来的，是「压根没让模型跑」**。
移植时这个性质必须保住，否则整个设计就垮了。

## 2. 目标框架的硬事实（都是读 NeoBot 源码确认的）

### 2.1 消息挂载点：`@plugin.message(rule=…, block=True)`

`packages/modloader/src/neobot_modloader/hooks.py` 里，`subscribe(..., block=True)`
会在处理器**返回之后**调 `ctx.consume()`；`app/src/neobot_app/runtime/gateway.py`
的 `handle()` 看到 `ctx.consumed` 就直接 `return`，消息不进回复管线。

⇒ 这就是「不调用原方法」的等价物。实测语义：0 token、不产生会话、模型不插话。

`rule` 会对**每条** message 事件跑一次（`dispatch.py` 先过 pattern 与 text/contains 过滤，
再调 `registration.rule(event)`），所以判定必须**同步、零 IO** —— 沿用原版
`takeoverKind()` 的约束。

### 2.2 处理器必须立刻返回

`neobot_adapter/onebot/adapter.py` 的 `_dispatch_loop` 是：

```python
event = await asyncio.to_thread(self._core.get_message, True, 0.1)
await self._dispatcher.publish(event)   # ← 串行
```

在处理器里 `await` 一次 60 秒的下载 = **所有群的收消息全部停摆**。
原版是 JS 异步回调、天然不阻塞；Python 里必须显式：

```python
@plugin.message(rule=..., block=True, priority=100)
async def _on_message(...):
    ...
    asyncio.create_task(runner())      # 判定完就把控制权还回去
```

同一会话的两首歌用 `asyncio.Lock` 串行，避免叠在一起发。

### 2.3 插件工具没有入站事件

`plugins/tools.py` 里，工具的 handler 被调用时 `event={}`、`message=Message({})`，
`Reply` DI 还会被**拒绝**（`_validate_tool_handler` 直接抛）。官方 minigame 的做法是
「用最近一次交互认人」，本插件沿用，但加了一条更严的规则（见 §5.2）。

### 2.4 语音条怎么发

`ctx.send_audio(conversation, path=…)` → `media_sender.send_audio()` →
`prepare_audio_segment()`：FileServer 开着给 HTTP URL，关着给 `file:///` →
adapter 发 `{"type": "record", "data": {"file": ...}}` → 协议端自己转码。

和原版一致：**插件只给本地路径，不自己转 SILK**。

### 2.5 配置与权限

- 配置：`plugin.toml` 的 `[config]` 是打包默认值，运行值在
  `plugins_data/<插件名>/config.toml`，宿主用 `Plugin(config=Model)` 校验后注入 `ctx.config`。
  键上方的注释会被面板渲染成字段说明。
- 权限：`ctx.plugin_host.services.get("command_service").permissions.can(uid, PERM_SUB_ADMIN)`
  → 官方权限体系（超级/次级管理员）。原版软查的 `permission.check`（admin-roster 提供）
  在 NeoBot 里不存在。
- 状态：原版的 `providers['status.netease-voice-song']` 改成能力（capability），
  调用方是 `ctx.require_plugin(...).call("status.netease-voice-song", {})`。

## 3. 设计映射

| 原实现 | 本实现 | 备注 |
| --- | --- | --- |
| `onIncoming` 补丁 + `decide()`/`handle()` | `@plugin.message(rule=…, block=True, priority=100)` | 语义等价，见 §2.1 |
| `handle()` 同步返回、异步发送 | `_dispatch()` 起 task + 会话级锁 | 见 §2.2 |
| `logic.js`（纯逻辑） | `logic.py` | 只依赖标准库，可离线测 |
| 曲库扫描（`node:fs`） | `library.py`（`os.scandir` + ID3v2/v1） | 扫描与读标签都进线程 |
| `netease-client.js` | `netease.py`（httpx） | 多接口降级、登录态、下载、缓存去重 |
| `logic.js` 里的下载流程 | `download.py` | 依赖注入，可拿假客户端测 |
| `plugin.json` 的 settings/configSchema | `plugin.toml [config]` + `config.py`（pydantic v2） | 面板表单 + 校验 |
| `providers` | `@plugin.capability("status.netease-voice-song")` | 结构化返回 |
| `api.config()` 现读 | `on_load` 读进内存；`config_hot_reload=true` 让面板保存即重载 | |
| `setInterval` 清临时文件 | 发送前 + 启动 + 卸载时清 | 不引入常驻定时器 |
| `DATA_DIR/voice-song/tmp` | `ctx.data_dir/tmp/songs` | |
| 手搓 GBK 码表（23940 项） | `bytes.decode("gbk")` | Node 的 Buffer 不认 gbk，Python 原生有 codec |

## 4. 模块划分与理由

```
__init__.py   只做「接线」：Plugin、消息钩子、工具、能力、生命周期
logic.py      解析 / 打分 / 限流 / 待选表 —— 不 import 框架，也不碰磁盘
library.py    曲库扫描 + ID3 —— 纯 IO，全部可丢线程
netease.py    网易云客户端 —— 网络 + cookie + 下载 + 缓存去重
download.py   搜歌→挑歌→下载的流程 —— 依赖注入，可替换音源
config.py     pydantic 模型 —— 面板表单与校验
```

为什么把下载流程从 `logic.js` 里拆出来单独成文件：它只依赖「客户端能力 + 配置」，
拆开之后可以用假客户端把「同名多首 → 选第 2 首 → 下载 → 落地」整条链跑通，
不需要联网。这在 Node 版里也是这么做的（`downloadSong` 的依赖注入），只是没有单独成文件。

## 4b. 1.8.0：加 QQ 指令（查状态 / 查曲库）

需求是「在 QQ 里用指令看登录状态和曲库」。看起来只是加两个命令，但有三处必须想清楚，
否则要么命令不生效，要么出现两条回复。

### 4b.1 命令必须排在「点歌」钩子之前让开

插件的消息钩子在宿主命令管线**之前**执行（`gateway.handle` 先跑 HookBus，再 route）。
而 `/点歌状态` 去掉斜杠后正好以触发词「点歌」开头 —— 不特殊处理的话，
它会被解析成点歌《状态》这首歌，然后被 `block=True` 吃掉，命令管线永远收不到。

所以 `_decide()` 里加了第 ⓪ 步：**本插件独占的指令名**（含别名、以及重名时宿主加的
`netease-voice-song__` 前缀形式）一律先交给命令管线。清单与注册用的是同一组常量，
避免两处漂移。

注意这条只针对**我们自己的**指令名：`/点歌 海阔天空` 不属于指令，仍然走点歌钩子，
所以「斜杠点歌」这个用法没有丢。

### 4b.2 群里 @ 与不 @：两条路径，但不能双发

NeoBot 的命令约定是「群里必须 @机器人，私聊不用」（`CommandService.handle_message` 里
`bot_account not in at_qqs` 就直接放手）。于是有两种尴尬情况：

- 群里没 @ 就发 `/点歌状态`：宿主不当命令 → 消息落到模型那里 → 用户觉得「指令没反应」；
- 如果插件无脑自己回，而宿主同时也会当命令处理 → **两条回复**。

处理办法是让插件判断「这条会不会被命令管线接走」：

```
会（私聊 / 群里 @了机器人） → 钩子让开，交给 CommandService（权限判定、/help、重名改名都归它）
不会（群里没 @）           → 插件自己兜住，用同一套渲染函数回复
```

判断错方向的代价不对称：猜「会」而实际不会，最多这条没响应；猜「不会」而实际会，
就是双回复。所以**拿不准时一律让开**（例如事件里没有 `self_id` 时）。

两个渲染函数（`_render_status` / `_render_library`）是唯一的实现，命令路径和兜底路径
都调它，所以两边输出永远一致。

### 4b.3 权限：不是「能不能用」，而是「能看到多少」

`/点歌状态` 里有两类信息：一类谁看都行（开关、触发词、曲库规模、限流、发了多少首），
一类属于「内部状态 → 群里可见」的泄露面（下载目录、登录态来自哪个客户端文件、上次错误原文）。

所以没有把整条命令做成管理员专属（那样普通群友会觉得「指令坏了」），而是：
命令本身人人可用，**细节按管理员身份分档**。管理员 = 配置里的 `admin_qqs`，
或 NeoBot 的超级/次级管理员（复用 `_is_admin`，与「解除点歌限制」同一套判定）。

### 4b.4 顺手修的两个显示问题

- 曲库列表按字符串排序时 `歌 (10)` 会排在 `歌 (2)` 前面 → 换成自然排序（数字段按数值比）；
- 文件名常是「歌手 - 歌名」，再拼一次 ID3 歌手就变成「歌手 - 歌名 — 歌手」→
  歌手已出现在名字里就不重复。

### 4b.5 验证

`run_framework_tests.py` 里新增 5 组断言（115 项总计）：指令注册（名字/别名/说明/用法）、
状态渲染（普通 vs 管理员、关下载时的措辞）、曲库渲染（总数/筛选/越界页码/翻页提示）、
「指令不会被点歌钩子吃掉」（没 @ 时兜住、@ 了让开、私聊让开、`/help` 不接管、
`/点歌 歌名` 仍生效）。

## 4c. 1.9.0：把「读本机客户端 cookie」换成手机扫码 + 降风控

### 4c.1 为什么必须换

1.7.0 的登录态是从本机已登录的网易云客户端文件里读的。这在「机器人就跑在你自己电脑上」
时能用，但一旦机器人跑在服务器/另一台机器上就完全失效——而后者才是常见部署。

换成扫码后链路变成：插件申请 unikey → 二维码内容就是 `https://music.163.com/login?codekey=<unikey>`
→ 用户手机 App 扫码确认 → 网易云在 `POST /api/login/qrcode/client/login` 的响应里下发
`Set-Cookie` → 插件保存并复用。全程不需要本机装客户端。

### 4c.2 三步状态机（和官方一致）

| 返回码 | 含义 | 插件的动作 |
| --- | --- | --- |
| 801 | 等待扫码 | 继续轮询 |
| 802 | 已扫码待确认 | 回一句「请在手机上确认」（只回一次） |
| 803 | 成功 | 保存 cookie、回成功、结束 |
| 800 | 二维码失效 | 回「重新发 /点歌登录」、结束 |

两个坑记住了：
- **803 但没拿到 MUSIC_U 不能算成功**。实测被拦时会出现「确认了但没给 cookie」，
  这时报成功会让用户以为能下载了，结果每首都是 -110。所以 `poll_once` 里显式判失败。
- **二维码发不出去要降级**。`qrcode` 依赖缺失、或 CommandService 没注入 file_server 时，
  图片发不出去——这时退回发登录链接，而不是「静默失败」。

### 4c.3 风控：把它拆成可执行的六条

用户要求「风控概率很低」。风控是对方的黑盒策略，没法证明「一定不触发」，但可以把
已知的诱因逐条消掉；每一条都对应代码里一个具体机制：

1. **频率**：`_wait_turn()` 让任意两次 API 至少隔 1.5 秒（可配），再加 0~0.8 秒抖动。
   固定节奏比随机节奏更像脚本。
2. **重复请求**：搜索结果按「关键词+条数」缓存 5 分钟；直链按「歌曲id+音质」缓存 5 分钟。
   「同一首歌被反复点」是最常见的重复来源，这一步能省掉绝大多数请求。
3. **硬撞限流**：某个搜索接口返回 405 之后，`_endpoint_cooldown` 记 10 分钟不再碰它。
   原实现是「换个写法继续试」，越试越久，最后连正常请求也被牵连——这次直接按接口隔离。
4. **风控冷却**：一旦看到 `-460`，记 `_risk_until = now + 5min`，期间所有请求直接快速失败
   并给出「还有 N 秒」的文案。风控期间继续请求只会加重。
5. **并发**：下载用全局 `Semaphore(1)`，多群同时点歌也只有一个在传。
6. **身份连续性**：保存**完整** Set-Cookie（MUSIC_U 之外还有 `__csrf`/`NMTID`/`NMCID`…），
   并且请求头补上 `Origin`/`Accept-Language`。只带一个 MUSIC_U 的请求在服务端看来不像客户端。

另外扫码轮询本身也放慢到 3 秒 + 抖动（官方客户端约 2 秒），并且**只在用户主动发
`/点歌登录` 时才轮询**，绝不后台自动重登——自动重登是最容易被判定为异常的行为之一。

### 4c.4 登录态存哪、怎么用

- 存 `plugins_data/<插件名>/netease_login.json`（`0600` 尽力而为），字段只有
  `source/saved_at/cookies`，**没有过期时间的概念**——过期由网易云返回 `-110` 自己暴露；
- `login_store` 里有一份内存态，`resolve_cookie` 每次下载都按
  **手填 > 扫码保存 > 本机客户端（需显式开启）** 的顺序取；
- 状态输出只显示「已登录 / 未登录 + 来源 + 多久之前」，**绝不回显 cookie 值**——
  这一条在 `describe()` 的测试里专门断言了（`"abc123" not in str(describe())`）。

### 4c.5 验证

`run_framework_tests.py` 新增 46 项断言（总计 162）：登录态存取/清理、`describe` 不泄露、
Set-Cookie 解析、801/802/803/800 状态机、「803 无 cookie 判失败」、二维码缺依赖时优雅降级、
发起→扫码→保存→状态可见的完整流程、非管理员被拒、登出删文件、节流参数夹取与风控快照。
网络层整体被替身替换，所以**这一步的测试不联网**。

## 4d. 1.9.1：`/点歌帮助`

需求是「给一条能看到所有快捷指令的指令」。看上去 `/help` 就够了，其实不够：

- `/help` 只列**注册进本体命令表**的命令，看不到「点歌 歌名」「来一首 xx」这类**自然说法**；
- 也看不到「解除点歌限制」——它不是命令，是消息钩子里的管理员指令；
- 触发词是可配置的，`/help` 里的静态文案不会跟着变。

所以单独做了 `/点歌帮助`，内容分三段（自然说法 / 斜杠指令 / 管理员），触发词从配置实时读；
普通群友还会多看到一行「找管理员把你加进 admin_qqs」。整段是纯字符串拼接（不读盘、不联网），
长度受 `_CMD_MAX_CHARS` 限制。

验证：`run_framework_tests.py` 新增 14 项（注册/别名/说明、帮助正文包含 7 个关键入口、
触发词来自配置、普通群友提示、长度上限、群里没 @ 时兜底路径也能回）。

## 4e. 1.9.2：指令改名（用户反馈「/点歌登录 像在点《登录》」）

### 4e.1 这个命名为什么会出问题

1.9.0/1.9.1 把指令都放在「点歌」前缀下：`/点歌登录`、`/点歌状态`、`/点歌乐库`。
实现上它们**确实**被正确分流了（`_is_own_command` 让消息钩子先让开，不会被当成歌名），
但**命名本身**就制造了歧义：同一屏里既有「点歌 海阔天空」（放歌）又有「/点歌登录」（登录），
用户只能靠记住「哪几个后缀是指令」来区分 —— 这正是用户反馈的点。

问题不在逻辑，在命名。所以按「点歌只负责放歌」的原则重排。

### 4e.2 新命名

| 旧 | 新 | 别名 |
| --- | --- | --- |
| /点歌帮助 | `/vs-help` | `/vs` |
| /点歌状态 | `/vs-status` | — |
| /点歌乐库 | `/vs-library` | `/vs-lib` |
| /点歌登录 | `/vs-login` | `/vs-qr` |
| /点歌登出 | `/vs-logout` | — |

`vs` = voice-song。点歌仍是 `点歌 歌名` 或 `/点歌 歌名`，不带任何后缀。

### 4e.3 旧名字怎么处理（这是关键细节）

直接把旧名字删掉会有个副作用：`/点歌登录` 不再属于任何指令，于是会落回**点歌钩子**，
被解析成「点一首叫《登录》的歌」——**恰好就是用户抱怨的那个现象**。

所以加了 `_LEGACY_COMMAND_MAP` 与 `_legacy_command_target()`：

- 只认「斜杠 + 一个完整旧名字」这种形态（`/点歌登录`、`/点歌乐库 2` 都算）；
- **不认带空格的**「/点歌 状态」—— 那是真点歌请求（歌名就叫「状态」），不能抢；
- 命中就回一句「已改名，请用 /vs-login」，并且**不进点歌流程**。

这条顺序也重要：旧名字检查排在 `_is_own_command` 和点歌解析**之前**，否则「/点歌状态」
会先被点歌解析吃掉。

### 4e.4 验证

`run_framework_tests.py` 新增 7 项（总计 183）：
- 注册表里五个 `vs-*` 都在，且**没有任何指令以「点歌」开头**；
- 别名 `/vs`、`/vs-lib`、`/vs-qr` 生效；
- 帮助正文包含全部新名字 + 「/点歌 海阔天空」+「解除点歌限制」；
- `_legacy_command_target`：`/点歌状态`→vs-status、`/点歌登录 取消`→vs-login、
  `/点歌 状态`→空、`/点歌海阔天空`→空；
- 旧名字发出来：接管、回提示、**不放歌**；
- `/点歌 状态` 仍判定为 `song`；
- `/vs-status` 没 @ 时兜底、@ 了让给命令管线、私聊让给命令管线。

## 5. 移植中发现的坑（按严重度）

### 5.1 ID3 标签读在事件循环上（严重）

**现象**：默认 `max_files=4000`、标签缓存首次为空，第一次点歌会 open + 读最多
1MiB × 4000 个文件，全部在协程里同步执行 → 所有会话的消息、心跳、回复一起卡住数秒到数十秒。

**根因**：把「扫描」丢进了 `asyncio.to_thread`，但「读标签」是另一个函数（`with_tags`），漏了。

**修法**：两件事一起做 ——
① `_tag_files()` 里 `await asyncio.to_thread(library.with_tags, …)`；
② `with_tags(..., budget_sec=2.0)` 加时间预算，预算用完就不读新标签，只用文件名匹配
（首次点歌不再能把整个曲库读一遍）。

**验证**：`run_tests.py` 里「预算为 0 时仍然返回候选 / 预算用完不读标签」；
`run_framework_tests.py` 的端到端路径也走这条。

### 5.2 工具路径会把语音条发到别的群（严重）

**现象**：A 群正在跟模型对话，B 群这时有人说了一句话 → 「最近交互」被顶掉 →
模型这一轮调 `play_local_song` 就把语音条发到 B 群；而且待选会记在 B 群那个人名下，
真正点歌的人回数字又被宽限期挡住 → **静默无响应**（正是原版注释里反复写的那个故障）。

**根因**：NeoBot 的插件工具没有入站事件（§2.3），「最近一次交互」是全局视角，
天生有歧义窗口。

**修法**：把规则改成「**有歧义就不猜**」：
- 调用方给了 `user_id` 且这个人在窗口内说过话 → 用他那个会话（明确的提示）；
- 否则只有「窗口内**只有一个**会话在活跃」时才敢投递；
- 其余情况返回一句明确的提示：让用户直接发「点歌 歌名」（那条走确定性路径）。

**验证**：`run_framework_tests.py`「工具路径：多个会话都在聊时不猜」——
两个会话各发一条后调用工具，断言「拒绝投递、没有音频发出」；给了 `user_id` 后再断言发到正确会话。

### 5.3 秒/毫秒混用（中）

`RateGate` 的清理阈值照抄了原版的 `3600_000`，但本实现的时钟是 `time.monotonic()`（秒），
结果「一小时」变成 41.7 天，`_last_by_chat` 超过 500 个会话后再也不缩小。

**修法**：`cutoff = current - 3600`，并在注释里写清「时钟是秒，别照抄原版的毫秒常量」。

### 5.4 取整方向（轻）

原版用 `Math.ceil`，移植时写成 `int(x) + 1`，剩余正好整数时提示数字会大 1
（「还要等 5 秒」显示成 6 秒）。统一改成 `math.ceil`。

### 5.5 三处下载调用丢了 try/except（轻）

原版三处都是 `try { downloadSong() } catch { {ok:false, error:'下载异常…'} }`。
直接 `await` 的话异常会逃出后台任务，变成一条「点歌任务异常」——
`stats.download_fails` 不涨、用户可能什么都收不到。
**修法**：`_safe_download()` 统一包一层，`CancelledError` 照常抛出。

### 5.6 数值配置没有上下界（轻）

原版 `cfg()` 里用 `clampNumber` 逐项夹到区间。移植时只保留了 pydantic 的类型，
`max_file_mb = -1` 会让每首歌都判成「太大」直接跳过；`ambiguity_ratio = 5` 会让
「难分高下」永不触发。**修法**：给这些字段加 `ge/le`，越界值由宿主回落默认值。

### 5.7 会话级状态只增不减（轻）

`locks` 与 `turn_plays` 都按 `chat_key` 记，从不清理。**修法**：`_prune_state()`
在状态量超过 200 时剪一次；只丢「没被持有」的锁（正在发歌的会话必须留着，否则同群两首歌会并发）。

### 5.8 `conversation_from_event` 在 try 外面（轻）

它在 `_dispatch` 里、`create_task` 之前调用。事件形状异常时异常会从 handler 抛出去，
HookBus 认为「没处理」→ `block` 静默失效、消息反而回到模型那边，同时 `_decisions` 留垃圾。
**修法**：把会话引用挪进任务里算，失败只让这次任务记日志。

### 5.9 下载闸的时机（对原版的修正）

原版在「列候选之前」就查下载闸。`always_ask=true`（默认）时每次点歌都走「列候选」这条路，
于是**同一首歌 10 分钟内第二次点歌会被静默丢掉**，哪怕只是想在缓存里再放一遍。

**修法**：列候选不算下载，只在真要下文件时查（`_handle_choice` / 工具里选完版本之后）。
真正下载前的那道闸仍然在，防刷意图不变。

### 5.10 缓存去重：只碰自己写的文件（安全加固）

去重会真删文件。原版只在「下载缓存目录」里做，但如果用户把 `download_dir` 指到自己的音乐库，
就会删他的歌。本实现只处理文件名带 `[网易云id]` 尾巴的文件 —— 那正是插件自己写的命名
（`_download_chosen` 恒为 `歌名 [id].mp3`），别人的文件一个都不碰。

**验证**：`run_tests.py` 里故意放一个 `我的收藏.mp3`（内容与重复项完全相同），断言去重后它仍在。

### 5.11 BOM 事故（工程）

`plugin.toml` 一度被编辑器写成带 UTF-8 BOM。Python 读 `.py` 能容忍 BOM，
但 `tomllib` **不能** —— 宿主会在加载清单时直接报错。
**修法**：所有文件统一无 BOM；`run_framework_tests.py` 里加了一条
「plugin.toml 没有 BOM」的断言，并用 `tomllib` 真解析一遍、核对
「清单默认值 == 模型默认值」，防止两边漂移。

### 5.12 一条评审误报（记录一下怎么核实的）

独立评审提出「候选同分时本地/网易云的先后反了」。核对原版：

```js
if (b.score !== a.score) return b.score - a.score;
const al = a.source === 'local' ? 1 : 0;
const bl = b.source === 'local' ? 1 : 0;
return al - bl;          // 同分：local(1) 排在 netease(0) 之后
```

本实现 `key=(score, 0 if local else 1), reverse=True` → 同分时 netease 在前，
与原版一致。**未改**。记下来是因为：评审有价值，但结论必须自己核对一遍。

### 6.2 为什么没在开发机跑真 NeoBot

开发机是 Python **3.9 + pydantic v1**，NeoBot 要求 **3.13 + pydantic v2**
（`ConfigDict` / `model_validate`）。

于是换了个办法：
- 业务模块（`logic/library/netease/download`）写成**只用标准库**，可以在 3.9 上直接测；
- 用 `selftest/stubs/` 里按 NeoBot API 形状做的替身把 `__init__.py` 真的加载起来，
  验证装饰器、DI、生命周期、端到端流程；
- 用 `check_framework_api.py` 拿**框架源码**做静态契约核对，确认没有任何「调了不存在的方法」。

⇒ 这三层能覆盖「接线错误」和「逻辑错误」，但**覆盖不了真机行为**（协议端、文件服务器、
网易云实时接口）。真机验证清单见 §8。

### 6.3 发布前的可安装性验证

用与 `PluginInstaller.install()` **完全相同**的方式验证仓库：

1. 下载 `https://codeload.github.com/<owner>/<repo>/zip/refs/heads/main`；
2. 解压后确认根目录只有**一个**含 `plugin.toml` 的目录（安装器的 `_extract` 要求）；
3. 校验 `plugin.toml` 的 `name` / `version`；
4. 校验 `raw.githubusercontent.com/.../plugin.toml` 可访问（面板「检查更新」用的就是它）。

## 7. 与上游 Node 版的差异

逐项列在 [README 的「与 Node 版的差异」](../README.md#与-node-版的差异都是被框架逼出来的不是随手改的)。
这里只强调三条**行为上真的会不一样的**：

1. 工具路径在多个会话同时活跃时**会拒绝投递**（§5.2）；
2. 发送失败**无法**把消息翻回未读让模型补救（`block` 在处理器返回时就完成了）——
   `reply_on_failure` 是唯一的提示通道；
3. 「同一首歌下载冷却」只在真要下载时生效（§5.9），因此缓存命中时可以反复点同一首。

## 8. 已知限制 / 未验证项

- **真机语音条未验证**：需要协议端支持 `record` 段（NapCat / LLOneBot / Lagrange 通常自带 ffmpeg）。
  若收到的是「文件」而不是语音条，先查协议端。
- **FileServer 关闭时的部署限制**：走 `file:///` 时，协议端必须与 NeoBot 同机。
- **网易云接口可能变**：搜索走 4 个接口自动降级，取直链 / 下载的接口若改动需要跟进。
- **工具路径的会话推断**天生有窗口（框架不给工具入站事件），已用「有歧义不猜」兜住，
  但连续对话场景下仍可能退回提示而不是直接发歌。
- **本机曲库非常大时**（几万个文件）仍受 `scan_depth`/`max_files`/时间预算限制，
  首次扫描可能不全 —— 调大 `max_files` 会相应变慢。
- 未做 `.ncm` 解密（明确不做：那是另一套东西，且绕过平台限制）。
